## Setting

- **Student (actor):** Megatron-LM training engine only (`README.md:233`, "Train engine | Megatron"). Example scripts: `Moonlight-16B-A3B-Instruct` (MoE, `run_moonlight_dsv3_training.sh:14`) and a Qwen smoke test (`test_qwen.sh`).
- **Rollout:** vLLM (SGLang partly wired, `megatron_workers.py:772`), run as a **separate inference-only worker group** on its own GPU pool (`rollout.nnodes` / `rollout.n_gpus_per_node`), disjoint from the actor pool. `hybrid_engine` is asserted off (`ray_trainer.py:327`).
- **Teacher:** a **separate, frozen vLLM server** behind a ZeroMQ proxy/worker pair (`teacher/proxy.py`, `teacher/worker.py`, `teacher/vllm_engine.py`), launched independently of training by `teacher/start_server.sh`. **Teacher is fixed** — there is no code path that updates teacher weights; the student only ever issues top-k logprob queries. (Script name `run_moonlight_dsv3_training.sh` implies a DeepSeek-V3-family teacher, but the checkpoint path is a placeholder.)
- **Domain/benchmarks:** none. `trainer.experiment_name: gsm8k` is a placeholder default (`config/on_policy_distill_trainer.yaml:292`); no evaluation is reported anywhere.
- **Framework:** verl, Ray single-controller. Teacher top-k transported as `teacher_topk_logps` / `teacher_topk_indices`.

## Async mechanism

**What is stale:** the *behavior student*. Rollouts for batch *i* are generated by the actor weights as of an earlier optimizer step than the weights that batch *i*'s gradient is applied to. The teacher is fixed, so teacher signal is never stale in the policy sense — but it is computed on the **stale rollout**, i.e. the teacher scores tokens the current student would not necessarily have produced.

**How staleness is bounded — structurally, by scheduler choice. There is no `max_staleness` parameter.** The only knob is

```yaml
# config/on_policy_distill_trainer.yaml:314
  scheduler: one_step_off
```

with `trainer.scheduler ∈ {one_step_off, two_step_off}`, dispatched at `ray_trainer.py:568-573`; anything else raises `TypeError`.

Each `update_policy` call is exactly **one optimizer step** (`megatron_workers.py:406` `zero_grad()` → micro-batch loop → `:429` `self.actor_optimizer.step()`), so "step" = optimizer step = data batch. In the example scripts `ppo_mini_batch_size == train_batch_size` (`test_qwen.sh:47,60`), confirming one update per rollout batch.

**`one_step_off_scheduler` (`ray_trainer.py:392-459`).** Steady state (`else` branch, `:440-454`) per loop index *i*: (1) sync actor→rollout weights and launch rollout for batch *i*; (2) wait on the previous teacher future; (3) `yield` batch *i−1*, which `fit()` then trains on. Because the rollout for batch *i* is launched **before** the update that consumes batch *i−1*, batch *i* was generated by weights that are exactly **one optimizer step behind** the weights its own gradient later updates. Warm-up 2 steps; during warm-up the sync is skipped (`:428`, `sync_before_generation=False`, comment "we don't need to sync weights here because we have not trained the actor yet").

**`two_step_off_scheduler` (`ray_trainer.py:461-531`).** Steady state (`:511-519`): consume the teacher future from *two* batches ago, launch the teacher request for the previous batch, then sync weights and launch the rollout for the current batch. Counting yields, the rollout for batch *j* is produced under θ_{j−2} and trained at θ_j → **exactly two optimizer steps** of staleness. Warm-up 3 steps.

**Range of staleness studied: {1, 2} optimizer steps. Nothing else is implemented and nothing is swept.** The "zero-step-off" (serial) baseline is only a figure in the docs; it is *not* a selectable scheduler in this recipe.

**Rollouts are NOT partial or continued across weight updates.** `async_generate_sequences` is a plain non-blocking alias for a full `generate_sequences` (`megatron_workers.py:755-756`):

```python
    def async_generate_sequences(self, *args, **kwargs):
        return self.generate_sequences(*args, **kwargs)
```

Every sequence in a batch is decoded end-to-end under a single weight version; weight sync is a whole-model NCCL broadcast between steps (`ray_trainer.py:326-329`). There is no replay buffer, no mixing ratio, no partial-rollout continuation. (verl-recipe has a separate `partial_rollout/` recipe; gkd does not use it.)

**No staleness metric is logged.** Emitted metrics are timings (`wait_prev_gen`, `wait_prev_teacher`, `wait_prev_prev_teacher`, `sync_rollout_weights`), sequence-length stats, MFU, and `actor/kl_loss` (`README.md:209-216`). No off-policyness measure, no behavior-vs-current log-prob ratio, no teacher/student top-k overlap diagnostic.

## Objective

Four distribution-level losses, all computed on the **teacher's** top-k support, selected by `distill_loss.name` and built at `megatron_workers.py:190`:

```python
        self.distill_loss_op = build_vocab_parallel_distill_loss(self.config.get("distill_loss", None)).cuda()
```

Defaults when `distill_loss` is absent (which it is in the shipped YAML): `name="kl"`, `rkl_ratio=0.1`, `beta=0.5` (`megatron_distill_losses.py:667-669`). The file header states the menu verbatim (`megatron_distill_losses.py:3-6`):

```
#   1) KL      : KL(P_topk || Q_full)  (teacher top-k truncated forward KL)
#   2) RKL     : KL(Q_hat_topk || P_hat_topk)  (pure reverse KL on renormalized top-k)
#   3) KL_RKL  : (1-r)*KL + r*RKL
#   4) JSD     : JSD_beta(P_topk, Q_full) with analytic rest term for Q||M outside top-k
```

**1. `kl` — `fkl`, teacher-top-k, NOT renormalized (default).** `megatron_distill_losses.py:106`:

```python
        per_token_kl_local = torch.sum(P_topk_part * (logP_topk_part - logQ_topk), dim=-1)  # [*]
```

i.e. $\ell_t = \sum_{v \in \mathrm{top}k(\pi_T)} \pi_T(v) \left[\log \pi_T(v) - \log \pi_\theta(v)\right]$, with $\pi_\theta$ the **full-vocab** softmax gathered at the teacher's indices (`:98-99`) and $\pi_T$ the raw teacher top-k probs, whose mass is $<1$ and is **not** rescaled.

**2. `rkl` — reverse KL on the TEACHER's top-k support, BOTH sides renormalized over that support.** `megatron_distill_losses.py:200-206`:

```python
        Q_hat = Q_topk / (Q_sum.unsqueeze(-1) + eps)
        P_hat = P_topk_part / (P_sum.unsqueeze(-1) + eps)
        ...
        per_token_rkl_local = torch.sum(Q_hat * (logQ_hat - logP_hat), dim=-1)
```

i.e. $\ell_t = \sum_{v \in \mathrm{top}k(\pi_T)} \hat\pi_\theta(v)\left[\log \hat\pi_\theta(v) - \log \hat\pi_T(v)\right]$ with $\hat\pi_\theta = \pi_\theta/\!\sum_{\mathrm{top}k}\pi_\theta$ and $\hat\pi_T = \pi_T/\!\sum_{\mathrm{top}k}\pi_T$. **Whose top-k: the teacher's** (`target_topk_indices`, supplied by the teacher server) — this is *teacher-top-k* RKL, not student-top-k. Conventions match ours (reverse KL = KL(student ‖ teacher)). Backward is the exact renormalized-simplex gradient, `grad = (Q/Z)·(a − E_{\hat Q}[a])` with `a = log Q̂ + 1 − log P̂` (`:242-250`).

**3. `kl_rkl` — convex mix** `(1−r)·KL + r·RKL`, `rkl_ratio` default 0.1 (`:364`, `:668`). The KL half is the *unnormalized* form, the RKL half the *renormalized* form.

**4. `jsd` — JSD_β(P_topk, Q_full)** with an analytic tail for the student mass outside the teacher top-k (`:499-522`): `M_k = βP_k + (1−β)Q_k` on the top-k, and outside it `M_j = (1−β)Q_j`, so the residual contributes `Q_rest·(−log(1−β))`. `beta` default 0.5.

**No sampled-token / policy-gradient form exists in this recipe.** There is no `k1`/`k3` estimator, no `sg[log π_T − log π_θ]` advantage, no `rkl_pg`. All four losses backprop directly through the student's probabilities via a TP-aware `torch.autograd.Function` invoked from a `logits_processor` on the last pipeline stage (`megatron_workers.py:317-329`).

**Aggregation:** plain token-mean over valid positions (`megatron_workers.py:304-305`, `masked_kl_lossed.mean()`), masked by `calc_kl_mask` = attention mask restricted to the last prompt token plus response positions (`:260-261`).

**Teacher top-k source:** vLLM `logprobs` / `prompt_logprobs` with `--n-logprobs` default **256** (`teacher/worker.py:29`; `teacher/start_server.sh:31` passes `--n-logprobs 256`), teacher sampling `temperature=0.8, top_p=0.95` by default (`teacher/vllm_engine.py:151-160`, `teacher/worker.py:63`); the student's k is taken automatically from the teacher's tensor width (`megatron_kl_loss.py:83`, and the docs say so at README.md:163).

**Stale artifact:** `megatron_kl_loss.py` — the single-loss forward-KL file the *docs* point at — is no longer imported by anything; `megatron_workers.py:30` imports from `megatron_distill_losses` instead. In `megatron_kl_loss.py` the teacher renormalization helper exists but its call site is **commented out** (`:42`, `# target_topk_logps = normalize(target_topk_logps)`).

**Implementation caveat (forward-KL gradient).** Both `megatron_kl_loss.py:134-141` and `megatron_distill_losses.py:121-126` use `grad = Q_full − P_sparse(topk)`:

```python
        # d/dz KL(P||Q) = Q - P_sparse(topk)
        grad_input = Q_full.clone()
        ...
        grad_2d[row, idx_2d] -= P_topk_part.view(-1, topk)
```

That is the exact gradient only if the teacher top-k mass sums to 1; the true gradient of the forward pass is $\left(\sum_k p_k\right) q_j - p_j$. So the backward implicitly treats the truncated teacher distribution as normalized while the forward does not. verl's **synchronous** core implementation handles this correctly, scaling by the teacher active mass $m_A$ (`verl@753aed3:verl/trainer/distillation/megatron/losses.py:239-246`). The `rkl` and `jsd` gradients here are self-consistent.

## Off-policy correction

**None. Zero.** A grep of the whole recipe for `importance`, `ratio`, `clip`, `old_log_prob`, `behav`, `icepop`, `truncat`, `tis` returns no correction machinery anywhere in `gkd/megatron/`. Specifically:

- No per-token importance ratio $\pi_\theta/\pi_{\text{behav}}$ — the rollout worker never returns behavior log-probs, and `update_policy` never requests them.
- No PPO-style clipping, no truncated importance sampling, no IcePop-style gating mask.
- The only mask applied is positional, not staleness-related (`megatron_workers.py:260-261`):

```python
                    calc_kl_mask = mb["attention_mask"].clone()
                    calc_kl_mask[:, : (-response_length - 1)] = False
```

- The KL/RKL/JSD loss is therefore applied to one- or two-step-stale samples **exactly as it would be to fresh ones**. The docs state this design intent directly: "This overlap preserves the same distillation objective while trading some strict on-policy guarantees…" (§1) and "the distillation objective is independent of how phases are overlapped" (§4).

Notably, the *only* importance-ratio machinery in verl's OPD stack (`clip_ratio: 0.2` with `old_log_probs`, and an optional `rollout_is_weights`) sits on the **synchronous** core path under `use_policy_gradient` (`verl@753aed3:verl/trainer/config/distillation/distillation.yaml:43-55`, `verl/trainer/distillation/losses.py:268-287`) — i.e. the corrected estimator exists in the repo but is wired into the *non-stale* trainer, and the *stale* trainer has none. (`rollout_is_weights` is verl's generic rollout-engine-vs-training-engine numerical-mismatch correction, not a staleness correction, and it too is absent from the async recipe.)

## Explanation offered

The only causal prose is about *why async was adopted*, i.e. a systems argument, never a learning-dynamics one (§1 Background, final paragraph, verbatim):

> "Built on verl's Ray-based single-controller components, we initially assembled a strictly on-policy KD pipeline where rollout generation, teacher knowledge acquisition, and policy optimization ran in lockstep. In practice, this synchronous design proved highly inefficient: the three stages had to wait for one another, creating pipeline bubbles and underutilized GPUs. To address this, we extend the asynchronous schedulers introduced by the One-Step-Off Policy pipeline to overlap these phases. This overlap preserves the same distillation objective while trading some strict on-policy guarantees for substantial gains in end-to-end throughput and hardware utilization."

Mechanism identified for the *objective's* choice (forward KL), from §2 — mode-covering, not staleness-related:

> "Objective: encourage student probabilities $Q$ to cover teacher modes $P$ using token-wise $\mathrm{KL}(P\,\|\,Q)$ computed on the teacher's top-k support."

The same rationale appears as a source comment (`megatron_kl_loss.py:101-103`, Chinese; translation mine): "KL(P‖Q) forces Q to cover all modes of P (avoiding missed peaks); KL(Q‖P) encourages Q to focus on a single mode of P (avoiding multimodality). Here we use KL(P‖Q), with P the target and Q the source, encouraging the source to learn all of the target's modes."

**No mechanism is offered for why one/two-step staleness is tolerable.** Support mismatch, MC-estimator variance, distribution shift, and student-weighting are never discussed. The implicit assumption is the "preserves the same distillation objective" claim — which is true of the loss *form* but says nothing about the expectation being taken under a stale state distribution.

## Same repo: is there a synchronous OPD recipe?

**Yes — a separate, first-class one in verl core**, and it is the better-maintained of the two: `verl@753aed3:verl/trainer/distillation/` with docs `verl@753aed3:docs/algo/opd.md` ("On-Policy Distillation (OPD)", author Jacob Helwig, "Last updated: 05/26/2026"). It is wired into `main_ppo` — when `distillation.enabled=true` the actor loss switches from `ppo_loss` to `distillation_ppo_loss` (opd.md:173-175).

Differences that matter for this sweep:

| | async recipe (`verl-recipe:gkd/megatron/`) | sync core OPD (`verl:verl/trainer/distillation/`) |
|---|---|---|
| Staleness | 1 or 2 optimizer steps (`trainer.scheduler`, default `one_step_off`) | **0** — teacher is served in-loop within the same step; no cross-step pipelining |
| `fkl` (teacher-top-k) | yes, default, **not** renormalized | yes, `forward_kl_topk`, k default **32** |
| `rkl` full/top-k | yes — teacher-top-k, **renormalized both sides** | no |
| `rkl_pg` (sampled-token) | **no** | **yes** — `kl, k1, abs, mse, k2, low_var_kl, k3`, default `loss_mode: k3` (`distillation.yaml:24`) |
| JSD / KL+RKL mix | yes (`jsd` β=0.5, `kl_rkl` r=0.1) | no |
| IS ratio / clipping | **none** | `use_policy_gradient` (default false) → PPO clip with `old_log_probs`, `clip_ratio: 0.2`, plus optional `rollout_is_weights` (`losses.py:279,287`) |
| Top-k overlap diagnostics | none | `distillation/overlap_ratio`, `student_mass`, `teacher_mass` (`megatron/losses.py:200-214`), explicitly "following 'Rethinking On-Policy Distillation of Large Language Models' (arXiv:2604.13016)" (`:200-201`) |
| Truncated-teacher gradient | `q − p` (assumes teacher mass 1) | scaled by teacher active mass `m_A` (correct) |
| Multi-teacher | no (single ZMQ server) | yes (`distillation.teacher_key` routing, MOPD) |
| Engines | Megatron only | Megatron + FSDP |
| Task rewards | no | `use_task_rewards: true` (RL + distillation jointly) |

Net: **the async path has the richer divergence menu but no correction and no sampled-token estimator; the sync path has the sampled-token reverse-KL estimator and the only clipping machinery.** The two are independent implementations that do not share loss code, and no one has compared them.

## Not in the source

- **No sync baseline of any kind.** The serial "zero-step-off" pipeline is drawn in a figure but is not runnable in this recipe, so no async-vs-sync comparison exists even in principle without code changes.
- **No accuracy, benchmark, or convergence evidence.** Nothing establishes that one- or two-step staleness is harmless for OPD; the claim is asserted ("preserves the same distillation objective"), never tested.
- **No end-to-end throughput number.** Only the two weight-sync micro-benchmarks (~3×, ~4×), with no absolute times or hardware.
- **No staleness metric or sweep.** Staleness is not measurable from the logged metrics, and only {1, 2} steps are implementable.
- **No off-policy correction stated or discussed.** Not even a sentence acknowledging that the expectation is now under a stale state distribution.
- **No guidance on choosing the divergence.** The `rkl` / `kl_rkl` / `jsd` losses are implemented but appear in no doc, no config, no example script, and no test — `distill_loss` is not a key in `config/on_policy_distill_trainer.yaml`, so reaching them requires `+actor_rollout_ref.actor.distill_loss.name=rkl`. Their existence is undocumented.
- **Dead config key.** `actor_rollout_ref.teacher.overlap_rollout: False` (`config/on_policy_distill_trainer.yaml:283`) is declared but read nowhere in the recipe.
- **Teacher temperature is silently 0.8 / top_p 0.95** (`teacher/worker.py:63` default) rather than 1.0, so the "teacher distribution" being matched is a tempered, nucleus-filtered one unless the caller overrides it — not mentioned in the docs.
- **Docs paths are stale**: they reference `recipe/gkd/megatron_kl_loss.py`, but the file now lives at `gkd/megatron/megatron_kl_loss.py` inside the `verl-recipe` submodule *and is no longer the loss actually used*.
